# Durable-intent Git drift predicates

## Decision

The current predicates are a safety baseline, not an extraction target:

- `inspectSingleMergeIntent` recognizes a single-plan squash on the default branch.
- `recoverApplyingBatchIntegrationAtRevision` recognizes one candidate squash in a batch integration worktree.
- `recoverCommit` recognizes a slice-completion commit on the plan branch and settles the slice with that exact recovered HEAD.

A shared extraction is a gated follow-up. It must preserve every safeguard below, including safeguards enforced by each predicate's caller, and must not turn a site-specific absence into permission to accept weaker evidence. The characterization tests are `internal/merge/crash_matrix_test.go` (single and batch merge) and `internal/run/crash_matrix_test.go` (slice completion). This document describes the code those tests pin; it does not propose a production change.

The plan mutation journal is a separate recovery boundary. As required by [Plan Mutation Journal](../plan-mutation-journal.md), a journal can recover plan artifacts but cannot prove that Git contains an intended commit. All three decisions below are based on live Git evidence.

## Side-by-side contract

| Site | Durable intent recorded before Git mutation | Live evidence re-derived on resume | Accept condition | Refuse condition |
|---|---|---|---|---|
| `inspectSingleMergeIntent` | `SingleMergeCommitIntent`: plan ID, source head, default branch, default parent, and exact trusted squash message. | Plan ID from the loaded plan; live default-branch selection; live plan-branch tip; live default-branch tip; if the tip advanced, that commit's first parent and message. It does not inspect worktree status. | The intent still names the loaded plan, live default branch, and live source tip. If default tip equals the recorded parent, return “not integrated” so the squash can run. Otherwise accept only a direct child of the recorded parent whose trimmed message equals the recorded message, and return “integrated.” | Refuse an intent/plan mismatch, default-branch mismatch, source-tip drift, unreadable evidence, or an advanced default tip whose parent/message is not the intended squash. |
| `recoverApplyingBatchIntegrationAtRevision` | Applying `BatchIntegration`: candidate plan ID, immutable source head, integration base SHA, and—on modern records—the exact commit message. The immutable `BatchCandidate` separately carries plan ID and source tip. | Caller-supplied current integration head; the parent and message of `revision` (`HEAD` normally, or the expected integration branch during workspace validation). It compares persisted source head with the candidate snapshot. It does not inspect worktree status or re-resolve the source branch in this helper. | Persisted source equals candidate source and base is non-empty. If current head equals base, return “not committed” so mutation can be rerun. Otherwise accept only a direct child of base whose message is either the exact recorded modern message or, for a historical empty-message intent, carries the exact final `Tao-Plan` and `Tao-Source-Head` trailers. | Refuse an intent/candidate source mismatch, empty base, unreadable parent/message, parent drift, or failure of the applicable exact-message/trailer rule. |
| `recoverCommit` | `SliceCommitIntent`: hash binding the completion inputs, policy, starting branch, starting head, exact final message, and creation time. Hash/proposal/branch checks occur in `Complete`; this predicate consumes the already-validated intent. | Parent and full message of the caller-supplied live plan-branch HEAD, then porcelain status of the execution worktree. The caller has already re-derived and matched the current branch and invokes recovery only after HEAD differs from the starting head. | HEAD is a direct child of the recorded starting head; its message, after removing Git's trailing newlines only, equals the recorded message; and status has neither commit-candidate paths nor ambiguous entries. Settle completion using that same recovered HEAD SHA. | Refuse parent drift, unreadable or mismatched message, unreadable status, any remaining commit candidate, or ambiguous status. Tao-owned metadata-only status is not a commit candidate and does not by itself refuse recovery. |

“Exact” above intentionally follows each current implementation's normalization; the normalization differences are classified below rather than silently unified.

## Crash-point matrix

The tests call the predicates directly with retained or synthesized intent so all sites can be compared at the same four Git states. “Before intent” is therefore characterization of the Git preimage, not a claim that production recovery can run without durable intent. Likewise, after ordinary settlement the caller may already have advanced or cleared lifecycle metadata and avoid this predicate; the row proves that the same Git postimage remains recognizable if recovery re-enters with the recorded intent.

| Crash point | Live Git evidence | `inspectSingleMergeIntent` | `recoverApplyingBatchIntegrationAtRevision` | `recoverCommit` |
|---|---|---|---|---|
| Before intent | Target HEAD is still the intended parent; worktree is clean. No intent is durable in the real protocol. | With the test's synthesized intent, accepts the preimage as safe to rerun and reports not integrated. Production requires an intent before entry. | With the synthesized applying record, accepts the preimage as safe to rerun and reports not committed. Production creates that record before mutation. | Direct recovery refuses because current HEAD is not a child of `StartingHead`. The enclosing completion flow would first record intent and, while HEAD still equals `StartingHead`, take the normal commit path instead of calling `recoverCommit`. |
| After intent, before Git mutation | Durable intent exists; target HEAD still equals the recorded parent; worktree is clean. | Reports not integrated; caller may perform the squash and commit. | Reports not committed; caller may restore to the base and perform the candidate squash and commit. | The enclosing flow sees HEAD equal `StartingHead` and performs the normal staging/commit path. A direct predicate call refuses parent mismatch, as pinned by the matrix. |
| After Git mutation, before settlement | Target HEAD is one new direct child of the recorded parent with the intended message; worktree is clean. | Recognizes the exact squash and reports integrated, preventing a duplicate merge commit. | Recognizes either the exact modern message or the legacy trailer-bound squash and reports committed, preventing duplicate integration. | Recognizes the exact commit, requires no residual commit candidates, and rolls lifecycle forward with the observed HEAD as `CommitSHA`. |
| After settlement | Git postimage is unchanged from the previous row; lifecycle settlement evidence exists in the fixture. | Still recognizes the squash from Git evidence; settlement metadata is not used as proof. | Still recognizes the squash from Git evidence; batch settlement metadata is not used as proof. | Still recognizes and settles the same HEAD from Git evidence; the direct test does not use prior settlement as proof. |

For all post-mutation acceptance, parent and message come from Git. A journal entry, an applying status, or a completion field alone is insufficient.

## Difference classification

The following inventory is intentionally conservative. **Load-bearing** means a future extraction must preserve the current distinction until a separate behavior-change decision and dedicated tests establish that changing it is safe.

| Difference | Classification | Judgment |
|---|---|---|
| Mutation target: live default ref vs integration worktree revision vs plan-branch HEAD | **Legitimate, site-specific** | Each operation owns a different ref/worktree. A shared helper may accept a revision, but callers must retain the correct ownership and branch/ref checks. |
| Pre-mutation result: merge predicates return a safe “not yet applied” result, while direct `recoverCommit` rejects an unadvanced HEAD | **Legitimate, site-specific** | Merge callers use their predicates both to decide rerun and to recognize roll-forward. Slice completion dispatches to `recoverCommit` only after its caller has observed `HEAD != StartingHead`; the normal path owns the unadvanced case. |
| Single merge re-resolves and pins plan ID, default branch, and live source branch inside the predicate | **Legitimate, site-specific, and load-bearing** | Single-plan state is spread across plan metadata and live refs, so these checks prevent applying stale reviewed work. They must not disappear merely because the other predicates receive already-bound inputs. |
| Batch compares persisted source head to the immutable candidate snapshot rather than resolving a live source ref in this helper | **Legitimate only with caller safeguards; load-bearing** | A batch integrates a frozen candidate SHA, and candidate/default/workspace validation occurs around this helper. Extraction must preserve that validation boundary and must not reinterpret the lack of a source-ref lookup as permission to accept a changed candidate. |
| Batch does not explicitly compare `integration.PlanID` with `candidate.PlanID` inside this helper, while single merge explicitly compares intent plan ID with loaded plan ID | **Accidental or not confidently legitimate; load-bearing** | Callers locate applying records by plan ID and persisted-progress validation supplies context, but the predicate itself relies on that pairing. There is no local semantic reason to accept a mismatched record. Do not normalize this by removing the single-plan check or by assuming the batch gap is harmless; a follow-up must characterize the caller invariant before changing it. |
| Batch accepts legacy records with no exact message by validating only the final Tao plan/source trailers | **Legitimate compatibility behavior; load-bearing** | Historical applying records predate exact message intent. Modern non-empty `CommitMessage` records require equality. Extraction must retain the two branches unless legacy support is deliberately retired. |
| Message normalization differs: single and modern batch compare `TrimSpace(live)` to the recorded message; slice completion removes trailing newlines only; legacy batch normalizes CRLF/outer whitespace while checking trailers | **Accidental or not confidently legitimate; load-bearing** | Git's `%B` output explains removal of a terminal newline, and trailer parsing has compatibility needs, but there is no documented cross-site reason for all whitespace differences. Preserve each current comparator exactly in an extraction; do not broaden or narrow matching without a separate decision. |
| Slice recovery checks worktree status; merge predicates do not | **Legitimate, site-specific, and load-bearing** | Slice completion is the boundary that centrally stages agent-written changes. Residual commit candidates could mean the recovered commit omitted work and therefore block settlement. Merge recognition proves a completed squash commit; surrounding Git operations/workspace validation own dirt and conflicts. A shared predicate must not drop the slice cleanliness gate. |
| Slice's “clean” gate permits status classified solely as Tao-owned metadata, while merge recognition has no equivalent classification | **Legitimate, site-specific** | Tao metadata must not be swept into an application commit. The predicate refuses commit candidates and ambiguous entries, not every porcelain line. |
| Parent evidence is read from default tip, a caller-selected batch revision, or a caller-supplied slice HEAD | **Legitimate, site-specific, but caller binding is load-bearing** | All require a one-commit advance from the recorded parent. Batch's revision-aware form intentionally supports checking a named integration branch while its status supplies `currentHead`; slice and normal batch callers pass the live HEAD. Extraction must prove that the inspected revision resolves to the head the caller intends to classify. |
| Single merge checks live source stability after intent; batch checks candidate snapshot binding; slice has no separate source-head field beyond `StartingHead` | **Legitimate, site-specific** | For slice completion, the worktree's starting commit is the parent being advanced, and the caller separately pins the starting branch. Merge operations consume a distinct source, so they need an additional source binding. |
| Slice validates intent hash, policy/proposal compatibility, branch, and protected-branch safety outside `recoverCommit`; batch validates candidate/workspace progress outside its helper | **Legitimate orchestration split; load-bearing** | The predicates are not complete authorization boundaries in isolation. Extraction may move code only if it carries these preconditions with it and keeps failures before mutation or settlement. |
| Roll-forward output: booleans/base for merge, direct lifecycle settlement with recovered SHA for slice | **Legitimate, site-specific** | Merge orchestration still has verification and settlement work. Slice recovery's purpose is to publish completion, and pinning `CommitSHA` to the observed accepted HEAD prevents metadata from naming another revision. |

No difference classified as accidental or uncertain is permission to “fix” it in the extraction. It is a requirement to preserve and test it until an explicit follow-up establishes a stronger common contract.

## Extraction gate

A future extraction may proceed only after review confirms that it:

1. keeps a real-Git crash matrix for all four points at all three call sites;
2. keeps both batch message branches and every refusal case (identity/source binding, parent drift, message drift, and slice worktree dirt);
3. identifies which caller owns branch, candidate, revision-to-head, and worktree validation rather than treating the helper as the whole authorization boundary;
4. derives acceptance from Git parent/message/HEAD/worktree evidence, never mutation-journal or lifecycle metadata alone; and
5. demonstrates that no documented safeguard is weakened.

Until those gates are met, the three predicates remain separate and unexported.
